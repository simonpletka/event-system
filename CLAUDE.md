**Real bug hit and fixed while wiring this up**: `signOut()` mutates cookies, which Next.js only permits from a Server Action or Route Handler — calling it inside `requireUser()` (invoked mid-render from Server Components) threw `Cookies can only be modified in a Server Action or Route Handler` on every request. Fixed by having `requireUser()` just `redirect("/login")` without clearing the cookie, and instead teaching the **login page itself** to check `active` before honoring an existing session and bouncing to `/dashboard` — otherwise a deactivated user's stale cookie would create redirect ping-pong (`/dashboard` → kicked to `/login` → bounced back to `/dashboard`). The cookie is inert either way since every protected route re-verifies `active`; it just isn't proactively cleared.

**Fixed the real confirm-dialog race (done):** the previous turn's "0 events in the DB" theory turned out to be only half the story — the user reproduced it again on a genuinely fresh `npm run dev`, deleting a time entry with no dialog at all, and pasted the terminal log showing `deleteTimeEntryAction` executing directly. That's a real bug, not a stale-cache artifact. Root cause: every confirm-gated destructive button was built as `<form action={serverAction}> onSubmit={(e) => { if (!confirm(...)) e.preventDefault() }}`, which relies on the browser's `onSubmit` handler's `preventDefault()` winning a race against React 19's own internal form-action dispatch (a separate "action" pseudo-event React's `extractEvents$1` creates for the same native `submit` event) — in practice that race doesn't reliably go the safe way. **Fix: decoupled confirmation from form submission entirely.** Every one of these is now a plain `<button type="button" onClick={...}>` (not inside a form-with-action at all) that calls `confirm()`/`alert()` synchronously first, and only *if approved* builds a `FormData` and invokes the imported server action directly inside `startTransition()` — matching the officially-supported "call a server action programmatically" pattern, with zero framework machinery in between that could race. Touched: `ConfirmDeleteButton.tsx` (shared — milestones/quotes/invoices/expenses), `DeleteEntryButton.tsx` (time tracker), `DeleteEventButton.tsx` (events, keeps its expense-count pre-check), the custom-role delete in `RolesTab.tsx` (calls the `useActionState` dispatch function directly instead of via `<form action>`), and `DeactivateButton` in `EditUserForm.tsx` (same anti-pattern, same fix, even though it's deactivate not delete). **Verified in an actual browser** (Chrome extension connected mid-session — first time browser access worked in this whole project): logged in as Admin, and for each of a time entry, an event with expenses, an event without expenses, and an expense, monkey-patched `window.confirm`/`window.alert` via the JS console to log calls and control the return value (rather than letting a real blocking native dialog hang the automation) — confirmed `confirm()` fires with the exact expected message, returning `false` correctly leaves the record untouched, and returning `true` actually deletes it; separately confirmed the expense-count gate's `alert()` fires with the exact message and `confirm()` is never even reached in that case. This is the first real end-to-end confirmation of the fix (earlier attempts to replicate a direct action call via curl hit a wall — `dispatchAppRouterAction` is wired into the full App Router client state machine, not a plain fetch, so it genuinely couldn't be faked from the command line).

## Tech stack

- Next.js **16.3.1** (App Router, TypeScript, RSC, Turbopack by default), project lives in `web/`. This is newer than most training data — `web/AGENTS.md` (auto-written by `next dev`) points at the bundled docs in `web/node_modules/next/dist/docs/`; read the relevant guide there before assuming Next 15-era APIs. Concretely: `params`/`searchParams` in pages are `Promise`s (must `await`), `middleware.ts` is renamed to `proxy.ts` (not used in this project — auth is checked per-layout/per-server-action instead, which is Next's own current recommendation), and parallel-route slots need a `default.js`.
- Prisma **7.9.1** — also a major-version jump from most training data. Breaking changes that bit during setup: `datasource.url` can no longer live in `schema.prisma` (goes in `prisma.config.ts` instead), SQL providers require an explicit driver adapter package (`@prisma/adapter-better-sqlite3` + `better-sqlite3` here), and the generated client lives wherever `generator client { output = ... }` points (`web/src/generated/prisma`, gitignored, import via `@/generated/prisma/client` and `@/generated/prisma/enums`) instead of `node_modules`. `prisma init` vendors a `.claude/skills/prisma-*` directory into the project with detailed migration guides — check there before fighting a Prisma error that looks version-related.
- SQLite (dev), via the adapter above
- NextAuth (Auth.js), Credentials provider only for now — bcrypt-hashed passwords, accounts are admin-seeded, no self-registration (per brief §2.1). Google OAuth provider to be added later purely via env vars once the user supplies Google Cloud credentials.
- Tailwind CSS v4, theme tokens taken directly from the wireframes (dark theme):
  - background `#131211`, surface `#1a1918`, text/border `#f3f2f2`, accent `#ec3013`
  - accent red is reserved for attention/primary actions only — not decorative
  - Neue Regrade font (self-hosted, `web/src/fonts/neue-regrade/` — a commercial font, not on Google Fonts, licensed for commercial use per `LICENSE.txt` there; loaded via `next/font/local` in `layout.tsx`, not `next/font/google`; replaced Archivo, which was only ever a Phase 1 placeholder pick), 2px rules on primary dividers / 1px on secondary, 0 border-radius everywhere
- `npm install` blocks postinstall scripts by default (npm 11's allow-scripts). When adding a new dependency that needs a postinstall (prisma, esbuild, native modules, etc.), run `npm approve-scripts <pkg>` after install or it silently won't work.
- `@react-pdf/renderer` (server-side invoice PDF generation, `src/lib/pdf/InvoicePdf.tsx`, rendered via `renderToBuffer` in a route handler — not part of the app's own React tree, so no version-conflict risk) + `qrcode` (renders the Czech "QR Platba" payment string to a PNG data URL for the PDF). Registers the Neue Regrade TTF via `Font.register()` rather than using the standard "Helvetica" font — Helvetica's WinAnsi/cp1252 encoding has no glyphs for ě/ř/ů/ď/ť/ň, so Czech diacritics were silently dropping from PDF output.
- **ARES** (`https://ares.gov.cz/ekonomicke-subjekty-v-be/rest/ekonomicke-subjekty/{ico}`) — free public Czech business-registry API, no auth/key required. `src/lib/ares.ts` does the fetch + shape-mapping (`obchodniJmeno`→name, `sidlo.textovaAdresa`→address, `dic`→DIČ), `src/app/api/ares/[ico]/route.ts` wraps it behind session auth, `src/hooks/useAresLookup.ts` is the client-side hook. Used by both the Event form (client/company fields) and Settings → Company.
- Uploaded expense receipts are stored on local disk at `web/uploads/receipts/` (gitignored, **not** under `public/`) and served only through an authenticated route handler (`src/app/api/uploads/receipts/[filename]/route.ts`) that checks the requesting user actually has access to the expense the receipt belongs to. Won't survive a redeploy to a stateless host — fine for local dev, would need object storage (S3-alike) before shipping anywhere else. Company logos follow the same disk-storage pattern at `web/uploads/logos/` (`src/app/api/uploads/logo/[filename]/route.ts`), but without the per-owner check — just requires being logged in, since it's shared branding, not per-user data.
- ESLint's `react-hooks/purity` rule flags `Date.now()` (but not `new Date()`) as an impure call inside a component body — write `new Date().getTime()` instead if a component needs "now".
- ESLint's `react-hooks/set-state-in-effect` rule flags calling `setState` synchronously at the top of a `useEffect` (e.g. seeding a ticking-clock value before starting the `setInterval`). Fix: use the lazy `useState(() => Date.now())` initializer for the starting value, and let the effect only set up the interval/subscription — see `TimerWidget.tsx` / `RunningTimerBox.tsx`.
- ESLint's `react-hooks/refs` rule flags writing to `ref.current` during render (the classic "always-latest callback ref" pattern). If a callback used inside an effect doesn't need to be in the dependency array because the effect itself unmounts the component before it could re-fire, just say so with an inline `eslint-disable-next-line react-hooks/exhaustive-deps` rather than reaching for a ref — see `QuickCreateEventModal.tsx`.

## Data model decisions

- `EventStatus` enum has the brief's 6 states **plus `CANCELLED`** — brief §4.3 explicitly invites adding a cancelled state ("klidně doplníme další stav, např. 'Zrušeno'"); added now since it's cheap pre-launch and painful to migrate later.
- Event detail layout: built as **3c (tabbed)**, not 3d (single-scroll) — user's explicit choice between the two wireframe options the brief left open.
- `TimeEntry` still exists only as a Phase 1 stub (Event-detail relation counts need it); `Quote`/`Invoice`/`Expense` are now the real Phase 2 tables.
- **Invoice numbering**: per-year sequences — quotes `YYYY-Q##` (unpadded), invoices `YYYY-####` (4-digit padded), computed at creation time from a count of that year's existing documents (`src/lib/document-number.ts`). Not safe under heavy concurrent writes (no locking), fine for this app's actual write volume.
- **`InvoiceStatus` has no stored `OVERDUE` value** — deliberately. It's `ISSUED | PARTLY_PAID | PAID` only; "overdue" is derived everywhere as `dueDate < now && status !== PAID` (`isOverdue()` in `src/lib/queries/finance.ts`, and inline in `StatusPill.tsx`). Storing it would go stale without a cron job.
- **VAT**: `CompanySettings.isVatPayer` flag + a per-line-item `vatRate` (defaults 21%, the standard CZ rate) — the business decision is data, not code. No editing UI for `CompanySettings` yet (Settings, Phase 4) — seeded directly with a real IBAN so the QR code has something to encode.
- **"Paid by" on an expense**: defaults to the current user. A non-card-holder can only submit as themselves; a card holder (or Admin/Accountant/Producer) gets a dropdown of all card holders plus themselves. This reconciles brief §5.3 (paid-by limited to card holders) with §2.2 (a Member can add their own expense) — it's a judgment call, not a direct spec quote.
- **Company overhead**: `Expense.eventId` is nullable rather than a fake pseudo-Event row; the new-expense form's event picker has an explicit "Company overhead — not tied to an event" option.
- **`CustomRole`** stores permissions as four tier enums (`EventsAccess`/`FinanceAccess`/`ExpensesAccess`/`SettingsAccess`), deliberately the same granularity the four built-in roles already use — not a generic permission-string/bitmask system. `User.role` (the built-in enum) is never nullable; when `customRoleId` is set, `role` just holds a least-privilege (`MEMBER`) fallback that's ignored, because `resolvePermissions()` in `authz.ts` checks `customRole` first. This avoided a nullable-column migration and means a defensive/missed call site still fails closed rather than open.
- **Invoice "History" panel** (`4c`) is a small, targeted `InvoiceEvent` action log (created/issued/payment-recorded/marked-paid), not a general audit log — that's still out of scope.
- **A running timer is a `TimeEntry` row with `running: true`**, not a separate concept — `startedAt` set, `endedAt`/`minutes` filled in on stop. Enforcing "only one running timer per user" is app-level (the start action stops any existing one first), not a DB constraint. `TimePhase` (Planning/Suppliers/On site/Wrap-up) is a new enum on `TimeEntry`, added specifically because Compare Events' "hours by phase" stacked bar (`5c`) needs it — the brief itself never names these phases, they're inferred from the wireframe's legend.
- **Compare Events' "cost per hour"** is just `event.quotedValue ÷ totalHours` — re-reading the wireframe numbers directly instead of inventing a per-user hourly-rate field. No schema needed for it.
- **"Invite user" (`5d`) creates the account immediately** with a random one-time password shown once in the UI, rather than a real emailed invitation — there's no email system (per Phase 1's auth decision) and the brief's own login model is "issued credentials," which this matches directly. There's no "pending invitation" state as a result — an account is either created or it isn't.
- **`User.lastSeenAt`** is updated on successful login only (not on every request) — cheap approximation of the wireframe's "Last seen" column without hammering the DB on every page load.

## Commands (from `web/`)

- `npm run dev` — dev server
- `npm run build` / `npm run lint` — typecheck + build / lint
- `npx prisma migrate dev` — apply schema changes locally
- `npm run seed:demo` (or `npx prisma db seed`) — wipes and reseeds the demo dataset (`prisma/seed.ts`): 4 users, 7 events, quotes/invoices/expenses/time entries, company settings.
- `npm run seed:empty` — wipes everything and leaves a genuinely blank slate: a single `admin@eventsystem.cz` login (password `changeme123`, same as the demo accounts) and nothing else — no events, quotes, invoices, expenses, time entries, custom roles or company settings.
- `npm run dev:demo` / `npm run dev:empty` — the two above, but each followed by `next dev` in the same command, since running a seed script alone just seeds and exits (it's not a server) — that confused the user into thinking something was broken ("it ends immediately") when really the seed step had just finished doing its one-shot job and there was no second step queued up to keep the process alive. These two scripts are the fix: one command reseeds *and* starts the server, so there's always a persistent process at the end. Plain `npm run dev` is unchanged — starts the server against whatever data already happens to be in `dev.db`, without touching it. **The dev DB is currently in the empty state** (as of 2026-08-17) — don't assume the demo dataset described elsewhere in this file is present; run `npm run seed:demo` (or `dev:demo`) first if a task needs it.
